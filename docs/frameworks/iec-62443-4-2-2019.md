# IEC 62443-4-2:2019 IACS component security — engagement guide

> Original operational guidance, not IEC text or a component-security certification.

## Source and applicability

The [IEC publication record](https://webstore.iec.ch/en/publication/34421), checked 2026-09-04, describes technical component requirements and component capability security levels. It explicitly excludes target and achieved security levels from its scope and says the August 2022 corrigendum is included. Confirm the licensed edition, corrections, component category and applicable assessment rules before detailed evaluation. Full requirements and evaluation methodology remain unverified for this draft.

Do not reproduce protected IEC requirements or place licensed text into AI prompts without permission. A component capability claim does not establish the security of its deployment or the surrounding industrial system.

## Engagement focus

Trace the exact component model, hardware revision, software/firmware build, enabled options and deployment assumptions to approved requirements and test evidence. Prevent results for one configuration from silently becoming claims about an entire product family.

## Roles

Product and engineering owners define the component and implementation. Security and qualified assessors determine applicability and evaluate evidence. Operations and safety authorities control any industrial test conditions. An independent reviewer challenges configuration coverage and claim boundaries. AI may organize permitted records and draft questions; it cannot test components under this review-only workflow, declare security levels, accept risk, authorize industrial changes or certify.

## Before starting

Record component identity, category, variants, interfaces, operating modes, dependencies, support state and intended use. Obtain approved requirements, scope decisions and authorized evidence. Identify test environments, confidentiality and source permissions. Documentation review does not authorize network connections, active discovery, firmware changes or customer-device tests.

## Ordered workflow

1. **Freeze the component boundary.** Reconcile every scoped model, revision, build and optional feature. Record what belongs to the component and what is provided by the environment. Missing configuration identity blocks reuse of dependent test results.
2. **Approve applicability and claims.** Qualified owners select applicable licensed requirements and enhancements for the component type and intended capability claim. Record rationale for exclusions. Do not infer a target or achieved system level from this component assessment.
3. **Trace implementation and assumptions.** Associate each requirement with actual implementation records, dependencies and customer configuration instructions. Separate native capability from environmental support. A feature listed in marketing is not evidence that it works in the assessed configuration.
4. **Prepare verification evidence.** Define approved expected outcomes, relevant interfaces and modes, test configuration and negative cases. Record the identity of the test artifact and method. Tests that could affect industrial operations need separate operational and safety authorization.
5. **Evaluate results and coverage.** Preserve observations, errors and limitations for every scoped requirement. Compare evidence with the approved objective. Report untested variants and unavailable records explicitly; a successful test on one revision does not automatically cover another.
6. **Remediate and retest.** Track defects to every affected version and requirement, obtain implementation approval and retest the corrected artifact. Revisit dependencies and documentation. Exception approval does not turn an observed failure into technical conformity.
7. **Bound the handoff and maintain it.** Deliver verified configuration details, evidence limits, installation assumptions, known issues and support obligations to the authorized reviewer. Approve external claim wording against the actual assessment outcome. Reassess after changes that affect the evaluated configuration or assumptions.

## Evidence and test plan

### 1. Component identity and applicability package

Product and engineering owners provide the complete variant/build register, interfaces, intended environment, licensed requirement references and applicability decisions. Reconcile each claim to its exact configuration. Record excluded variants and missing evidence without treating them as passing.

### 2. Implementation and verification package

Security and quality owners provide design/configuration evidence, test objectives, artifact identities, results, limitations and defect links. Check whether expected security behavior was observed under the stated conditions. Preserve all evidence supplied for assessment without silent trimming or sampling. Full inventory coverage is not proof that every technical combination was tested.

### 3. Integration guidance and maintenance package

Support and lifecycle owners provide customer prerequisites, secure configuration guidance, vulnerability records, update decisions and change-impact reviews. Trace each assumption to an accountable party and evidence. Record component capability, customer enablement and system-level verification separately. A released patch is not proof of field installation.

## Failure branches and decisions

- Test report omits firmware identity: obtain the missing identity before applying its results to a release.
- Security behavior depends on an external service: record the dependency and approved assessment treatment; do not attribute its entire behavior to the component.
- Updated variant changes an interface: have qualified owners determine affected requirements and retesting; do not inherit all old results automatically.
- A test fails or has no usable output: retain the failure or uncertainty and escalate rather than recording a pass.
- Customer configuration violates documented prerequisites: distinguish that deployment gap from the bounded component evidence.

Use [agent runbook](../agent-runbook.md) assertions: supported, not_supported, inconclusive, not_applicable and not_tested. These are evidence statuses, not security levels or certification decisions.

## Cadence and renewal

Review relevant releases, vulnerability findings, dependency changes and changed deployment assumptions. Set additional intervals through approved obligations and risk decisions. Do not invent universal annual certification duties or treat the publisher's stability date as a product expiry.

## Completion and handoff

Deliver the configuration register, applicability decisions, requirement/evidence links, test coverage, known limitations and open actions with owners and dates. Fictional author desk case: firmware A has a passing authentication test, but firmware B adds an untested maintenance interface. The result supports only the tested configuration and objective; the new interface is not_tested. A claim that every interface in firmware B is verified is unsupported.
