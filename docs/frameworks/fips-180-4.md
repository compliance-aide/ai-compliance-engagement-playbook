# FIPS 180-4 secure-hash engagement guide

> Original operational guidance, not FIPS secure-hash content, an algorithm-selection decision, an approval, or a compliance claim. Confirm current material through [FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final) and the organization’s approved cryptography, security, architecture, legal, and operational decisions.

## Engagement focus

Operate a governed lifecycle for in-scope secure-hash uses. Connect each use case to an approved purpose and scope, protected data and system context, implementation and configuration decisions, protocol and signature dependencies where relevant, interfaces, access, logging, validation, supplier dependencies, changes, incidents, transition planning, and retirement. A configuration extract, implementation record, supplier statement, test result, or audit log is evidence to assess; none alone proves suitable hash use, correct implementation, protected data, approved use, secure operation, or compliance.

## Source and applicability

The [NIST publication record](https://csrc.nist.gov/pubs/fips/180-4/upd1/final), read 2026-09-04, identifies the August 2015 edition and a March 2023 decision to revise it. A revision planning note is not an effective replacement. Verify the current publication, algorithm-transition guidance and use-specific requirements before selecting or accepting an algorithm. Full standard text and current transition rules remain to be reviewed; these original checks are not a substitute for cryptographic design review.

## Roles

Cryptography and security owners approve purpose, algorithm and parameters. Application owners identify the bytes processed and the decision made from the digest. Platform and supplier owners provide implementation evidence. Independent reviewers challenge traceability and conclusions. AI can organize authorized evidence; it cannot select cryptography, change production settings, approve exceptions, accept risk or attest to compliance.

## Before starting

Record the use case, system, exact algorithm/variant, input contract, implementation version, output format, downstream consumer and expected security property. Distinguish an unkeyed digest from a message authentication code or digital signature. Use the [agent runbook](../agent-runbook.md) and approved synthetic QA data. Keep confidential inputs, keys and sensitive derived values outside this repository.

## Ordered workflow

1. **Map each use to its purpose.** Inventory in-scope file checks, protocol dependencies, signatures and other hash uses. Output a purpose register with approved design references. A matching digest alone does not establish sender identity or a trusted origin.
2. **Define the exact input.** Record encoding, normalization, framing, byte length and any preprocessing or truncation. Output an input contract. Two systems hashing different representations can both compute correctly while failing the intended comparison.
3. **Identify the implementation.** Link the operation to the actual library/module, version and configuration. Output an implementation map. Installed packages or algorithm names in documentation do not establish the executed path.
4. **Check computation in QA.** Use authoritative test vectors appropriate to the selected variant and separately test the application's actual input handling. Preserve empty, boundary-length, binary and streaming cases as applicable to the approved scope. Output expected/actual results and untested cases; successful vectors do not prove certification or suitability.
5. **Check the consuming decision.** Test matching, altered, missing and malformed digest inputs against the predefined acceptance rule. Verify where the expected digest comes from and how that source is trusted. Output decision evidence; recomputing a digest from an untrusted replacement file cannot authenticate that file.
6. **Trace failures and changes.** Record algorithm/variant changes, provider updates, encoding changes and downstream compatibility. Preserve old and new identifiers without silently mixing them. Output migration/retest actions and a named owner for legacy verification needs.
7. **Prepare the bounded conclusion.** Separate computation correctness, input coverage, reference trust, consumer behavior and approved use. Output a source-linked draft with all gaps; do not promote one passing comparison to whole-system integrity or compliance.

## Evidence and test plan

### Hash use and data flow

Application, platform, data and cryptography owners provide the complete in-scope use inventory, approved design references, input contracts, implementation identifiers and downstream decisions. Reconcile each use to its source bytes, transformations, digest representation and consumer. Record unresolved uses instead of omitting them from a favorable summary.

For each integrity claim, identify how the expected digest is obtained and protected. Preserve the distinction between an independently trusted reference and a digest delivered through the same untrusted path as the file. A hash can identify bytes without proving who supplied them. An inventory of hashes also does not prove that every required record was collected; reconcile the evidence population separately.

### Implementation and release

Engineering, quality and release owners provide build provenance, actual deployment identifiers, approved test cases, expected results and defect records. Tie every result to the executed variant and version. Record authoritative vector identifiers separately from application-specific test cases. Preserve failures, skipped cases and instrumentation limits; one passing vector cannot support an exhaustive correctness claim.

Check the application's exact bytes and result parsing with synthetic inputs. Include the authorized use's streaming behavior, encoding, output length and malformed-input handling. Distinguish digest mismatches from read failures or unavailable reference data. A failed file read must not become the digest of an empty input and then appear as a valid comparison. Verify that the consumer records a failure distinctly and follows its approved handling path.

### Lifecycle, exceptions and transition

Security, supplier and records owners provide current source reviews, dependency notices, approved exceptions, incidents and transition plans. Reconcile all affected producers, stored references and consumers when the algorithm, variant or representation changes. Preserve algorithm identifiers and input-contract versions with historical digests; a string of the right length does not establish the intended variant.

Record which legacy records still need verification and who owns the migration decision. Do not silently recompute historical references from potentially altered data or overwrite prior adverse results. For each exception, verify scope, conditions, authorized decision and review trigger. A proposed transition is not an implemented change; obtain post-change observations for every affected in-scope path.

## Failure branches and decisions

Unavailable implementation evidence is `not_tested`; unresolved use-specific applicability is `inconclusive`. A known mismatch against a predefined input contract is `not_supported`, even if the underlying algorithm passes vectors. Preserve that distinction and route design questions to the qualified owner.

Fictional desk case: a producer hashes UTF-8 bytes with a final newline; a consumer removes that newline before hashing. Both implementations pass their algorithm vectors, but the application's exact-byte comparison fails. Algorithm-vector results are `supported`; the agreed end-to-end input contract is `not_supported`. The agent records the byte representations and does not disable comparison to make the workflow pass.

## Cadence and renewal

Review after source, algorithm-policy, input-format, implementation, provider or consumer changes and after integrity incidents. Set scheduled checks from approved organizational requirements; do not invent quarterly reviews or annual FIPS renewal. Preserve a named owner for transition decisions and legacy data verification.

## Completion and handoff

Deliver the complete use/data-flow inventory, input contracts, implementation and build map, vector and application-test results, reference-trust evidence and lifecycle register. State separately what the evidence supports about computation, exact input coverage, trusted reference and consumer behavior. Name untested paths and unresolved algorithm-policy questions, with next owners and actions.

Independent source, skeptical and rights review remain required before publication. Qualified owners retain cryptographic design, exception, transition and compliance decisions. This draft has not validated an implementation or established that any real system protects data correctly.
