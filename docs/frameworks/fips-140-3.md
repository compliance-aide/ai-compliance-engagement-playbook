# FIPS 140-3 cryptographic-module engagement guide

> Original operational guidance, not the FIPS publication, CMVP instructions, a validation certificate, an authorization decision, or a compliance claim. Confirm current requirements and validation status through [FIPS 140-3](https://csrc.nist.gov/pubs/fips/140-3/final) and the organization’s approved security, legal, procurement, engineering, and operational decisions.

## Engagement focus

Manage the organizational use, procurement, integration, and lifecycle oversight of cryptographic modules where FIPS 140-3 is applicable. Maintain a governed inventory that ties each in-scope product, module boundary, version, operating mode, deployment, dependency, approved use, validation-status evidence, and change history to the relevant system and risk decision. Treat a product claim, a certificate reference, or a successful technical check as evidence to verify—not proof that a deployed configuration is within a validated boundary, suitable for its use, or compliant.

## Source and applicability

Use the current FIPS publication, CMVP guidance, exact certificate and associated security policy. Official indexed [CMVP validation-process information](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/cmvp-flow) checked 2026-09-04 identifies module version, operational environment and vendor as certificate details. Full current program rules, transitions and deployment-specific security policies remain to be verified. This guide supports organizational use and procurement; it does not replace laboratory validation or authorize a cryptographic configuration.

## Roles

Security and compliance owners determine applicability. Cryptography/platform engineers identify actual module use and configuration. Procurement and supplier owners obtain authoritative evidence. System owners manage approved changes. Independent reviewers challenge traceability and claims. AI may reconcile authorized metadata and prepare workpapers; it cannot validate a module, accept risk, approve cryptography, change production settings or attest to compliance.

## Before starting

Record system, use case, requirement source, cryptographic operations, deployment environments and review period. Obtain authorized inventory/configuration access and name the security decision owner. Use the [agent runbook](../agent-runbook.md) to set expected results before checking them. Keep keys, secrets and customer data out of this repository; use synthetic input in an approved QA environment.

## Ordered workflow

1. **Establish applicable use.** Link each in-scope cryptographic operation to its system and approved requirement. Output an operation inventory. A blanket product label does not identify which module handles storage, transport, signing or other distinct operations.
2. **Identify the actual module.** Record vendor, module name, software/firmware/hardware version, boundary and environment from authorized deployment evidence. Output a deployment manifest. An installed library is not proof the application invokes it.
3. **Retrieve authoritative validation evidence.** Match each module to the certificate, current status, caveats and linked security policy. Record retrieval date and exact references. Output a status register; algorithm testing, a vendor claim or an in-process listing must not be substituted for module validation evidence.
4. **Compare configuration with scope.** Have the qualified owner evaluate version, environment, approved services and required configuration against the security policy and current program guidance. Record exact mismatches and unresolved applicability. Output an assessment matrix; a general FIPS-mode switch is not sufficient evidence for every operation.
5. **Observe the integration.** Under approved QA authority, collect evidence of the module used by each defined operation and the applicable mode/service indicators. Preserve expected behavior, actual observation and instrumentation limits. Output operation-specific results without exposing sensitive key material or claiming a laboratory validation.
6. **Reconcile changes.** For patches, builds, platform changes and provider updates, identify affected operations and prior evidence requiring reassessment. Preserve the before/after baseline. Output assigned gaps; neither a security patch nor an unchanged product name automatically proves continued coverage.
7. **Review the bounded claim.** Separate certificate status, deployment match, actual module use and organizational suitability. Provide evidence and open exceptions to the authorized owner. Output a draft decision packet; do not promote a supported module assertion into whole-system compliance.

## Evidence and test plan

### Module boundary and approved use

Cryptography, architecture and system owners provide the complete operation/module inventory, approved use decisions, version manifests, environment details and boundary references. Reconcile every in-scope operation to an observed implementation or an explicit evidence gap. Include separate transport, storage, signing and recovery paths where present; evidence for one path does not establish another.

For each association, record the source of the module identity and the observation method. Distinguish package installation, runtime loading and actual operation routing. Preserve the limits of instrumentation: a process listing may show a loaded library without showing which implementation served a particular operation. Do not capture keys or sensitive plaintext to make the record appear more complete.

### Validation status and supplier evidence

Procurement, security and supplier owners provide official certificate references, linked security-policy versions, acquisition specifications, supplier claims and notices. Match vendor, module version, environment and caveats explicitly. Keep vendor statements as vendor evidence rather than replacing authoritative program records with marketing material.

Record status and lookup time independently from deployment match. If current status or a transition's implications are unclear, obtain a qualified owner determination from current CMVP guidance; do not automatically interpret a historical or changed status as either universal permission or universal prohibition. A revoked, superseded or otherwise changed entry must not be hidden by retaining only an older favorable screenshot. Preserve the history and current uncertainty.

### Deployment changes and exceptions

Platform, change and risk owners provide actual deployed manifests, approved configurations, changes, incidents, exceptions and reconciliation results. Reconcile the complete scoped deployment population and preserve unmatched versions and unavailable environments. A successful QA result does not prove production uses the same build or settings.

For each change, record affected operations, implementation evidence, required reassessment and post-change observation. Verify that an approved exception covers the exact system, scope, conditions and period; an exception request is not approval. Keep a security defect and a validation-coverage question as separate tracked concerns so one does not disappear when the other is resolved. Authorized owners decide remediation and risk; this review does not direct agents to weaken security to preserve a certificate match.

## Failure branches and decisions

Unavailable deployment evidence is `not_tested`; unresolved certificate coverage is `inconclusive`. A directly observed operation using a different module contradicts a predefined required-module criterion and is `not_supported`. Preserve this failure even when the intended module is installed and has supporting validation evidence. Do not infer that another module lacks validation merely because the expected certificate does not cover it.

Fictional desk case: a QA application includes the required module, but its signing path loads a different library. Installation is `supported`; use of the required module for signing is `not_supported`. The alternate library's validation status is unresolved. The agent records the loaded-component evidence and routes correction to engineering instead of changing crypto settings itself.

## Cadence and renewal

Set review frequency from current program requirements and approved organizational policy. Recheck certificate status, security-policy changes, advisories, module versions and deployment changes before relying on prior conclusions. Do not invent quarterly reconciliation or annual certificate renewal as universal FIPS requirements. Assign the next review owner and trigger.

## Completion and handoff

Deliver the operation/module map, complete deployment manifest, authoritative status and policy references, applicability matrix, observation records, change reconciliation and open exceptions. State separately what is known about certificate status, deployment coverage, actual module use and approved organizational use. Carry every untested environment and unresolved interpretation into the handoff with a named owner and next action.

Require independent source, skeptical and rights review before publication. Qualified authorities retain procurement, cryptographic configuration, exception and compliance decisions. The packet is a draft evidence assessment, not a CMVP validation or system authorization. No actual cryptographic module or deployment has been assessed by this guide's fictional case.
